# Честный знак без ТС ПИоТ: как проверяем коды до подключения Атола

Собрано 21 октября 2026. Касса: Атол Онлайн (облачная, API v5, ФФД 1.2), товар: одежда (лёгкая промышленность), продажа только через свой сайт с полной предоплатой, отгрузка с нашего склада через Яндекс Доставку и СДЭК (они только везут, чек не пробивают).

Код: `apps/backend/src/lib/chz.ts` (проверка), `apps/backend/src/lib/kassa.ts` (чеки). Настройки: `DEPLOY.md`, раздел «Касса: Атол Онлайн».

## Коротко

1. **Разрешительный режим к нам применяется.** Честный знак прямо разбирает схему «свой магазин, предоплата»: проверка на складе при сборке, код, факт и время проверки сохраняются, затем идут в закрывающий чек. Исключение для дистанционной продажи (ППРФ 1944, п. 3, пп. «е») — только когда чек пробивает третье лицо, например курьер с кассой. У нас чек пробиваем мы сами, поэтому исключение нас не касается. [1]
2. **Проверяем сами по API ЧЗ, токеном X-API-KEY.** Это и есть «текущая схема с использованием xAPI key», о которой пишет Атол (ответ поддержки R1844427, октябрь 2026): ТС ПИоТ у Атола ещё «стабилизируется», срок около двух недель. До тех пор Атол просит проверять коды по старой схеме.
3. **В чек — отраслевой реквизит при каждом коде:** `federal_id 030`, `date 21.11.2023`, `number 1944`, `value UUID=<reqId>&Time=<reqTimestamp>`. Это теги 1262–1265 внутри 1260, поле `sectoral_item_props` в API Атола. [2][3]
4. **Сроки противоречат друг другу** (подробно ниже). Честный знак: отключение токена «начинается с 1 октября 2026, поэтапно», дата полного отключения не названа. Атол: 21 октября велит пока работать токеном. Наш токен 21 октября работал: площадки ответили, проверка вернула reqId.
5. **Когда Атол включит ТС ПИоТ**, переключаем `KASSA_PROVERKA_KM=tspiot`. Дальше Атол проверяет коды сам и сам пишет реквизит. Код переписывать не нужно.

## 1. Нужен ли нам разрешительный режим

- Одежда под разрешительным режимом: онлайн-проверка обязательна с 1 ноября 2024, офлайн (локальный модуль) — с 1 марта 2025 в рознице и с 1 мая 2025 в крупных сетях. [4][5]
- Облачных касс это тоже касается: «Разрешительный режим касается любой розничной торговли». Проверка — забота кассового ПО, касса лишь записывает в чек факт и время проверки, которые ей передали. [6]
- Дистанционная продажа. Статья Честного знака «Схема работы дистанционной торговли при разрешительном режиме» [1] в таблице:
  - FBS/DBS **без** делегирования: режим не применяется (исключение п. 3 пп. «е»), продавец сам подаёт вывод из оборота;
  - **свой магазин, предоплата: применяется**, «проверка на складе при сборке, данные сохраняются для закрывающего чека»;
  - «срока годности факта проверки нет», в чеке указывается **последний** факт и время проверки.

  Исключение действует, только если отгружаем покупателю через третье лицо, которое не участник оборота, **но применяет ККТ**, то есть пробивает чек. Яндекс Доставка и СДЭК у нас только везут, денег не берут.
- Внешние статьи пишут, что «разрешительный режим не распространяется на дистанционную продажу» [7]. Это упрощение: оно верно для схемы, где чек пробивает доставка или платёжный агент. **Противоречие**, держимся официальной статьи ЧЗ [1].

## 2. API проверки кода

Источник: «Методические рекомендации по реализации запрета продажи…», Оператор-ЦРПТ, **версия 08 от 15.11.2024** [2]. Свежее официальной версии в открытом доступе я не нашёл. Честный знак обещал обновлённое «Руководство по обмену информацией», но в сентябре 2026 его ещё не было [8].

| Что | Как |
|---|---|
| Продуктивный контур | `https://cdn.crpt.ru` |
| Тестовый контур | `https://markirovka.sandbox.crptech.ru`, нужен токен, полученный именно в тестовом контуре |
| Авторизация | заголовок `X-API-KEY: <токен>`, один раз, без дублей; `Content-Type: application/json; charset=utf-8` (другие кодировки и дубли заголовков ЧЗ отклоняет) |
| Где взять токен | кабинет ЧЗ, «Профиль», «Токен для контрольно-кассовой техники». Один на ИНН, на все кассы. Опубликуешь — заблокируют |
| Список площадок | `GET /api/v4/true-api/cdn/info`. Обновлять не чаще раза в 6 часов, хранить; если метод недоступен — работать по сохранённому списку |
| Выбор площадки | `GET <площадка>/api/v4/true-api/cdn/health/check` на каждой, первой берётся самая быстрая по нашему замеру |
| Проверка | `POST <площадка>/api/v4/true-api/codes/check`, тело `{"codes": [...], "fiscalDriveNumber": "16 цифр ФН"}`. Код целиком, с криптохвостом, символ GS (ASCII 29) экранируется как `\u001d`. Номер ФН необязателен, но рекомендуется: при подозрениях ЧЗ заблокирует одну кассу, а не весь токен |
| Ответ | по каждому коду `found, valid, verified, utilised, realizable, sold, isBlocked, ogvs, isOwner, errorCode`, на весь запрос `reqId` (UUID) и `reqTimestamp` (миллисекунды, UTC) |
| Назначение | метод только для проверки перед розничной продажей (ППРФ 1944, п. 13) |
| Лимиты | числа в методичке нет; есть 429 «повторить» и требование держать одно соединение. Сколько кодов можно в одном запросе — не опубликовано, мы режем по 100 |

**Когда продавать нельзя** (раздел 4 методички):
- `found=false` или `utilised=false` — кода нет или он не нанесён;
- `verified=false` — не прошла криптопроверка;
- `sold=true` — уже выведен из оборота;
- `isBlocked=true` — заблокирован госорганом;
- `sold=false` и `realizable=false` — не введён в оборот.

Сверх этого мы запрещаем коды с `valid=false`, с ненулевым `errorCode` и **чужие коды** (`isOwner=false`). Закон чужой код не запрещает, но для нас это ошибка склада. Отключается так: `CHZ_TOLKO_SVOI=false`.

**Ошибки** (раздел 1.4.3):

| Ответ | Что делать |
|---|---|
| 401 | токен неверный, повторять бессмысленно |
| 429 и 5xx | повторить; не помогло — площадку на 15 минут в сторону, идти к следующей |
| прочие 4xx | ошибка в запросе, не повторять |
| 5xx с `code 5000` в теле | не ответила страна-эмитент: площадку не трогать, повторить один раз |
| 1,5 секунды без ответа три раза подряд | площадку на 15 минут в сторону |
| `203` на любом методе | в ЧЗ объявлена авария: проверки отключить, продавать без них |

Авария действует ещё 3 дня после окончания, тег 1260 в это время не заполняется (раздел 7).

## 3. Что кладём в чек Атола

- **Предоплата 100 %** (`payment_method full_prepayment`, `payment_object 1`): кодов нет, проверки нет. Так советуют Честный знак [1] и сам Атол [9]: при предоплате два чека — при оплате без кода, при передаче с кодом.
- **Полный расчёт** (`full_payment`, `payment_object 33`, зачёт предоплаты `payments.type 2`) — по позиции на каждую пару. В каждой позиции:
  - `mark_code.gs1m` — код целиком в Base64;
  - `mark_processing_mode "0"`, `planned_status 1`;
  - `sectoral_item_props: [{federal_id "030", date "21.11.2023", number "1944", value "UUID=<reqId>&Time=<reqTimestamp>"}]`.

  Реквизиты 1262–1264 одинаковы для всех групп товаров (раздел 3.1 методички [2]). Формат поля — из документации Атола v5 [3].
- Флаги `use_tspiot` и `permissive_mode` в режиме `chz` **не ставим**. Атол пишет: без `permissive_mode` «проверку КМ по разрешительному режиму необходимо предварительно проводить… и результат проверки самостоятельно указывать в sectoral_item_props чека» [3]. С `use_tspiot=true` и без касс с ТС ПИоТ чек упадёт с ошибкой `TSPIOTRequired`.
- Проверку делаем **в момент отправки чека**, сразу после сборки. Если Атол не ответил, повтор уходит с той же проверкой: ЧЗ заново не спрашиваем. Первый чек мог пройти, и повторная проверка ответила бы «уже продан».

## 4. Если что-то не так

| Случай | Что делает наш код |
|---|---|
| Код нельзя продавать | чек не отправляется, статус `fail`, причина при каждом коде (без криптохвоста), тревога на почту и в админку. Дальше человек: правильный код от склада или другая пара |
| ЧЗ не отвечает (сеть, 5xx, 429, 5000, тайм-аут) | чек остаётся в очереди, сторож чеков пробует каждые 5 минут, через час тревога. **Без проверки не продаём**: методичка до 1 марта 2025 разрешала продавать без ответа, а теперь нужна офлайн-проверка, а локального модуля у облачной кассы нет |
| 401, нет токена | как «не отвечает», только в журнал пишется ошибка; через час тревога |
| 203, авария | чек уходит без реквизита 1260, в заказе отметка `avariya` |

## 5. Возвраты и вывод из оборота

- **Вывод из оборота** делает сам чек «полный расчёт» с кодами: Атол передаёт его в ОФД, оттуда в ЧЗ. Отдельный документ «вывод из оборота» в кабинете ЧЗ **не подаём**: сведения передаются один раз, одним способом [1]. Вручную в кабинете (причина «дистанционная продажа») выводят, только если чек пробивает не продавец — наложенный платёж через службу доставки [1][9]. У нас такого нет.
- **Возврат предоплаты** (заказ не собран или отменён до сборки): чек `sell_refund` без кодов, проверка не нужна. Так уже работает.
- **Возврат вещей после полного расчёта**: автоматизации нет, приходит тревога, чек возврата с кодами делаем вручную. Разрешительный режим по ППРФ 1944 — это запрет **продажи**, поэтому для чека возврата проверку не делаем. Отдельного официального разъяснения про возврат я не нашёл.

## 6. Сроки и что изменится

| Дата | Что | Источник |
|---|---|---|

| 01.07.2026 | продажи без ТС ПИоТ фиксируются как отклонения и уходят контролирующим органам | ЧЗ через «Фармвестник», 09.07.2026 [11] |
| 01.10.2026 | токен X-API-KEY продлён «до 1 октября» как временная мера; отключение «начинается с 1 октября 2026», поэтапно, дата полного отключения не названа | ЧЗ [8][11]; Контур пишет, что с 1 октября токен перестаёт работать [12] |
| 21.10.2026 | наш токен работает (проверено, раздел 7) | |
| ~начало ноября 2026 | Атол обещает подключить ТС ПИоТ «в течение двух недель» после ответа | поддержка Атола, R1844427 |

**Противоречия:**
- Методичка версии 08 пишет, что токен действует до 1 марта 2026. Позже срок двигали на 30 июня, потом на 1 октября [10][11]. Официального текста, который продлевал бы токен **после** 1 октября, я не нашёл. При этом и Атол, и сам ЧЗ на деле ещё работают с токеном. **Риск:** ЧЗ может отключить токен в любой день. Тогда проверка отвечает 401, чеки «полный расчёт» встают в очередь, через час приходит тревога (продаж без проверки не будет). Выход один: ТС ПИоТ.
- «Продажи без ТС ПИоТ — отклонение с 1 июля» [11]. Значит, даже с нашей проверкой и реквизитом 1260 ЧЗ может отмечать отклонения, пока у кассы нет ТС ПИоТ. Штраф автоматически не назначается, решает проверяющий [8]. Сделать с этим мы ничего не можем, пока Атол не готов. Ответ поддержки Атола (R1844427) стоит сохранить как подтверждение, что задержка на стороне кассы.

**Когда Атол включит ТС ПИоТ:**
1. Купить лицензию ЕСП на кассу (ЗН 00104826693190) — это делает Тимофей, кабинет ЕСП уже заведён.
2. Атол подтверждает, что ТС ПИоТ подключён к кассам группы.
3. В `.env` на сервере `KASSA_PROVERKA_KM=tspiot`, перезапустить medusa-server и medusa-worker. Чеки из очереди уйдут уже с `use_tspiot` и `permissive_mode`; реквизит Атол заполнит сам. Если реквизит уже стоит (чек проверили до переключения), Атол допишет результат в тег 1265 [3].
4. `CHZ_TOKEN` можно оставить: в режиме `tspiot` он не используется.
5. Список проверок разрешительного режима настраивается в кабинете Атола [3]. Включить стандартные: код есть, в обороте, не продан, не заблокирован.
