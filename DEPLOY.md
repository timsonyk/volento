# Volento — развёртывание

Интернет-магазин женских классических брюк. Бэкенд Medusa v2, витрина Next.js.

## Что где живёт

| Что | Где |
|---|---|
| Код | `/home/volento/volento` на сервере |
| Бэкенд Medusa | `apps/backend` |
| Витрина Next.js | `apps/storefront` |
| Секреты бэкенда | `apps/backend/.env` (права 600, в git не попадает) |
| Секреты витрины | `apps/storefront/.env.local` (права 600, в git не попадает) |
| Пароли БД и админки | `/root/.volento-secrets` (только для root) |

Адреса: витрина — `https://slytn.ru`, API — `https://api.slytn.ru`, админка — `https://admin.slytn.ru`.

Админка намеренно отключена на `api.slytn.ru` (там `/app` отдаёт 404): у неё отдельное имя. Оба имени ведут в один и тот же процесс на порту 9000.

## Сервисы

Все три поднимаются автоматически после перезагрузки сервера.

```bash
systemctl status medusa-server       # API + админка, порт 9000
systemctl status medusa-worker       # фоновые задачи, порт 9001
systemctl status volento-storefront  # витрина, порт 8000
```

Логи:

```bash
journalctl -u medusa-server -f
journalctl -u volento-storefront -f
```

Все три слушают только `127.0.0.1` — наружу их выпускает исключительно nginx.

## Обновление кода

```bash
cd /home/volento/volento
sudo -u volento git pull

# если менялся бэкенд
cd apps/backend
sudo -u volento env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=3072 npx medusa build
cd .medusa/server && sudo -u volento npm install
systemctl restart medusa-server medusa-worker

# если менялась витрина
cd /home/volento/volento/apps/storefront
sudo -u volento npm install
sudo -u volento env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=3072 npm run build
systemctl restart volento-storefront
```

`NODE_OPTIONS=--max-old-space-size=3072` обязателен: на 2 ГБ памяти сборка без него падает с нехваткой памяти. Работает за счёт файла подкачки на 4 ГБ.

## Фотографии товаров

Лежат в `/var/lib/volento/uploads`, отдаёт их nginx по адресу `https://api.slytn.ru/static/...`.

Два места, где легко наступить на грабли:

**Папку нельзя переносить внутрь проекта.** Medusa по умолчанию складывает загрузки в `.medusa/server/static`, а эту папку команда сборки удаляет целиком — все снимки товаров пропали бы при первом же обновлении кода. Путь задаётся переменной `UPLOAD_DIR`.

**Папку нельзя держать в домашнем каталоге пользователя.** `/home/volento` закрыт правами `750`, nginx туда не зайдёт и отдаст 403. Поэтому `/var/lib/volento`.

При добавлении нового домена его нужно прописать в `apps/storefront/next.config.js` в `images.remotePatterns`, иначе Next откажется показывать картинки.

## Баннер на главной

Меняется из админки: **Товары → «Баннер главной страницы» → Медиа**.

Это служебная запись с адресом `home-banner` и меткой `system`. Medusa не хранит произвольные картинки сайта, зато хорошо хранит изображения товара — поэтому баннер оформлен товаром, а админка даёт готовый интерфейс загрузки. Из каталога такие записи спрятаны фильтром в `listProducts` (через него идут все списки), своей страницы у них нет — она отдаёт 404.

**Порядок картинок важен:** первая — для компьютера, вторая — для телефона. Если второй нет, на телефоне показывается первая.

Требования к файлам:

| Где | Размер | Пропорции |
|---|---|---|
| Компьютер | 2560×1440 | 16:9 |
| Телефон | 1080×1920 | 9:16 |

Формат JPEG или WebP, вес до 500 КБ. Баннер растягивается на весь экран под шапкой и **обрезается по краям** — на широких окнах срезается верх и низ, на узких бока. Значимое (логотип, надписи, лицо модели) держать в средней части: примерно 70% ширины и 85% высоты.

Текст лучше не вшивать в картинку: на телефоне он мельчает, поисковики его не видят, а поменять слоган можно только перерисовав файл. Если нужен текст поверх — скажите, положу настоящими буквами.

Если запись удалить или убрать из неё картинки, витрина покажет запасной файл `apps/storefront/public/banner.jpg`.

## Резервное копирование

Каждую ночь в 03:30 UTC снимаются копии базы (хранятся 14 дней) и фотографий товаров (последние 3 архива) в `/var/backups/volento/`. Фотографии копируются отдельно не зря: в дампе базы лежат только ссылки на файлы, и без архива снимков восстановленный магазин будет с пустыми карточками.

```bash
systemctl list-timers volento-backup    # когда следующий запуск
/usr/local/bin/volento-backup.sh        # снять копию прямо сейчас
ls -lh /var/backups/volento/            # что уже есть
```

Восстановление из копии:

```bash
. /root/.volento-secrets
sudo -u postgres createdb -O volento volento_restore
gunzip -c /var/backups/volento/volento_ГГГГ-ММ-ДД_ЧЧ-ММ.sql.gz \
  | PGPASSWORD="$DB_PASSWORD" psql -h 127.0.0.1 -U volento -d volento_restore
```

Восстанавливать сначала в отдельную базу, посмотреть, что данные на месте, и только потом заменять рабочую. Проверка восстановления делалась — дамп разворачивается полностью.

## Скрипты

Лежат в `scripts/` в репозитории, на сервер ставятся копированием:

| Скрипт | Что делает |
|---|---|
| `backup.sh` | Копия базы и фотографий, стоит в `/usr/local/bin/volento-backup.sh` |
| `build-backend.sh` | Сборка бэкенда и установка зависимостей в собранную папку |
| `rebuild-storefront.sh` | Полная пересборка витрины с нуля |
| `seed-test-catalog.js` | Тестовый каталог: модели, цвета, фотографии, остатки |
| `smoke-test.sh` | Проверка цикла товар → корзина → сумма |

Конфиг nginx лежит в `deploy/nginx/volento.conf` — это выгрузка рабочего файла с сервера, включая блоки, которые дописал certbot.

## Переменные окружения

`apps/backend/.env` — значения смотреть на сервере, здесь только имена:

```
NODE_ENV, DATABASE_URL, REDIS_URL, EVENTS_REDIS_URL, WE_REDIS_URL, CACHE_REDIS_URL,
JWT_SECRET, COOKIE_SECRET, AUTH_MFA_ENCRYPTION_KEY,
STORE_CORS, ADMIN_CORS, AUTH_CORS
```

Redis разделён по базам: `/0` сессии, `/1` события, `/2` движок процессов, `/3` кеш.

`WORKER_MODE` и `ADMIN_DISABLED` в `.env` не задаются — их выставляют systemd-юниты, чтобы один и тот же код работал и как сервер, и как воркер.

`apps/storefront/.env.local`:

```
NEXT_PUBLIC_MEDUSA_BACKEND_URL, NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY,
NEXT_PUBLIC_BASE_URL, NEXT_PUBLIC_DEFAULT_REGION
```

Все переменные витрины с приставкой `NEXT_PUBLIC_` попадают в код, который выполняется в браузере покупателя. Поэтому `NEXT_PUBLIC_MEDUSA_BACKEND_URL` — это публичный адрес `https://api.slytn.ru`, а не внутренний `127.0.0.1:9000`. Секреты в переменные с такой приставкой класть нельзя.

## Структура каталога

Заложена сознательно, менять осторожно:

- **Товар** — модель определённого цвета, со своим артикулом (например, «Брюки классические прямые, чёрный», артикул `VLT-001-BLK`).
- **Вариант** — размер + рост. У каждого свой SKU.
- **SKU** — формат `АРТИКУЛ-РАЗМЕР-РОСТ`, например `VLT-001-BLK-46-170`. Должен совпадать со складским посимвольно: к нему будет привязана синхронизация остатков.
- **Остатки** ведутся на уровне варианта, на складе «Основной склад».
- Регион «Россия», валюта — рубль.

**Почему цвет — отдельный товар, а не опция варианта.** Каталог в Medusa перечисляет товары, а не варианты. Если бы цвет был опцией внутри товара, модель попадала бы в каталог одной карточкой, и показать её же в трёх цветах тремя карточками было бы нельзя. Плюс фотографии в Medusa привязаны к товару, а не к варианту — при переключении цвета снимки не менялись бы. И артикул со склада уже содержит цвет, иначе два цвета одной модели давали бы одинаковый SKU.

**Как цвета связаны между собой.** У каждого товара есть метка `model:<КОД МОДЕЛИ>` и поля `model`, `article`, `color`, `color_hex` в metadata. Компонент `ColorSelect` на витрине находит по метке остальные цвета модели и рисует переключатель.

Слабое место: метка и поля заполняются руками, опечатка молча выкинет цвет из переключателя. При импорте каталога это должно заполняться автоматически из выгрузки.

## Что настроено на сервере

- Ubuntu 26.04, вход по SSH только по ключу, пароль отключён
- ufw: наружу открыты только 22, 80, 443
- PostgreSQL 18 и Redis 8 слушают только `127.0.0.1`
- Файл подкачки 4 ГБ (`/swapfile`)
- nginx как обратный прокси, HTTPS от Let's Encrypt с автопродлением
- Приложение работает под пользователем `volento` без прав администратора

## Особенности, о которых стоит помнить

**Витрина вне общего пространства зависимостей.** Стартер Medusa рассчитан на pnpm; при установке через npm зависимости «поднимаются» в корень, и Next начинает видеть React 18 от бэкенда вместо React 19. Сборка падает с React error #31. Поэтому `apps/storefront` исключён из `workspaces` в корневом `package.json` и имеет собственный `node_modules`. Не возвращайте его в workspaces без перехода на pnpm.

**Патч в `apps/storefront/src/middleware.ts`.** За обратным прокси Next не доверяет заголовку `Host` и подставляет `localhost:8000`, из-за чего покупатель уезжает на несуществующий адрес. Origin для перенаправления собирается из заголовков `x-forwarded-host` / `host`, которые проставляет nginx. При обновлении стартера патч нужно накатить заново.

**Откуда берётся витрина.** Из официального шаблона `medusajs/dtc-starter` — это тот же монорепозиторий, из которого `create-medusa-app` разворачивает бэкенд. Отдельный репозиторий `medusajs/nextjs-starter-medusa` заархивирован в июле 2026 и больше не обновляется; брать код оттуда не надо.

**Сборка витрины обращается к API по публичному адресу.** `NEXT_PUBLIC_MEDUSA_BACKEND_URL` попадает в браузерный код, поэтому там публичный `https://api.slytn.ru` — и при сборке сервер стучится сам к себе через внешний интерфейс. Такая петля ненадёжна и один раз уронила сборку по таймауту. В `/etc/hosts` на сервере добавлено `127.0.0.1 api.slytn.ru`, чтобы запросы шли сразу на локальный nginx. На браузеры покупателей это не влияет.

**Не пересобирайте витрину одновременно с изменением каталога.** Сборка собирает данные страниц из API; если в этот момент товары пересоздаются, сборка падает.

**Перевод витрины.** Русский текст вписан прямо в компоненты, библиотеки локализации нет — магазин одноязычный, и лишний слой абстракции тут не нужен. Обратная сторона: при обновлении витрины из upstream переводы придётся накладывать заново. Формат цен и дат задаётся локалью `ru-RU` в `src/lib/util/money.ts` и в местах вывода дат.

**Кеш витрины.** Список товаров кешируется Next.js. После изменений в каталоге новые товары появляются не сразу. Немедленно — так:

```bash
rm -rf /home/volento/volento/apps/storefront/.next/cache
systemctl restart volento-storefront
```
