# Volento — развёртывание

Интернет-магазин женских классических брюк. Бэкенд Medusa v2, витрина Next.js.

## Что где живёт

| Что | Где |
|---|---|
| Код | `/home/volento/volento` на сервере |
| Бэкенд Medusa | `apps/backend` |
| Витрина Next.js | `apps/storefront` |
| Секреты бэкенда | `apps/backend/.env` (права 600, в git не попадает) |
| Секреты витрины | `apps/storefront/.env.local` (права 600, в git не попадает) |
| Пароли БД и админки | `/root/.volento-secrets` (только для root) |

Адреса: витрина — `https://slytn.ru`, API — `https://api.slytn.ru`, админка — `https://admin.slytn.ru`.

Админка намеренно отключена на `api.slytn.ru` (там `/app` отдаёт 404): у неё отдельное имя. Оба имени ведут в один и тот же процесс на порту 9000.

## Сервисы

Все три поднимаются автоматически после перезагрузки сервера.

```bash
systemctl status medusa-server       # API + админка, порт 9000
systemctl status medusa-worker       # фоновые задачи, порт 9001
systemctl status volento-storefront  # витрина, порт 8000
```

Логи:

```bash
journalctl -u medusa-server -f
journalctl -u volento-storefront -f
```

Все три слушают только `127.0.0.1` — наружу их выпускает исключительно nginx.

## Обновление кода

```bash
cd /home/volento/volento
sudo -u volento git pull

# если менялся бэкенд
cd apps/backend
sudo -u volento env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=3072 npx medusa build
cd .medusa/server && sudo -u volento npm install
systemctl restart medusa-server medusa-worker

# если менялась витрина
cd /home/volento/volento/apps/storefront
sudo -u volento npm install
sudo -u volento env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=3072 npm run build
systemctl restart volento-storefront
```

`NODE_OPTIONS=--max-old-space-size=3072` обязателен: на 2 ГБ памяти сборка без него падает с нехваткой памяти. Работает за счёт файла подкачки на 4 ГБ.

## Фотографии товаров

Лежат в `/var/lib/volento/uploads`, отдаёт их nginx по адресу `https://api.slytn.ru/static/...`.

Два места, где легко наступить на грабли:

**Папку нельзя переносить внутрь проекта.** Medusa по умолчанию складывает загрузки в `.medusa/server/static`, а эту папку команда сборки удаляет целиком — все снимки товаров пропали бы при первом же обновлении кода. Путь задаётся переменной `UPLOAD_DIR`.

**Папку нельзя держать в домашнем каталоге пользователя.** `/home/volento` закрыт правами `750`, nginx туда не зайдёт и отдаст 403. Поэтому `/var/lib/volento`.

При добавлении нового домена его нужно прописать в `apps/storefront/next.config.js` в `images.remotePatterns`, иначе Next откажется показывать картинки.

## Оформление сайта

Картинки и надписи главной правятся на своей странице админки: пункт **«Главная»** в левом меню. У каждого места своя подпись, нужный размер и кнопка загрузки — считать порядок картинок больше не нужно.

Как это устроено: страница живёт в `apps/backend/src/admin/routes/glavnaya`, а хранится всё в метаданных служебной записи «Оформление сайта» (адрес `home-banner`, метка `system`). Medusa не умеет хранить произвольные картинки сайта, зато умеет метаданные и загрузки; из каталога такие записи спрятаны фильтром в `listProducts`, своей страницы у них нет — она отдаёт 404. Витрина читает ключи через `apps/storefront/src/lib/data/home-banner.ts`.

**Ключи картинок:**

| Ключ | Где показывается | Размер |
|---|---|---|
| `верх_телефон` | верхний баннер, телефон | 1080×1350, 4:5 |
| `верх_компьютер` | верхний баннер, компьютер | 2560×1600, 8:5 |
| `середина` | между разделами и низом | 1600×1600, квадрат |
| `низ_телефон` | нижний баннер, телефон | 1080×1350, 4:5 |
| `низ_компьютер` | нижний баннер, компьютер | 2560×1440, 16:9 |
| `плитка_<адрес раздела>` | плитка раздела на главной | 1200×1800, 2:3 |

**Ключи надписей:** `надпись`, `ссылка_текст`, `ссылка_адрес` — текст поверх верхнего баннера; `акция_текст`, `акция_показывать` — полоса над шапкой.

Без нижних картинок внизу повторяется верхний баннер. Плитка раздела без своей картинки берёт фото товара из этого раздела, а если товаров нет — раздел на главной не показывается.

Формат JPEG или WebP, вес до 500 КБ. Картинки обрезаются по центру, если пропорции файла не совпадают с указанными: значимое держать в средней части кадра. Текст в картинку вшивать не нужно — он задаётся ключами и рисуется настоящими буквами.

Раньше место картинки задавалось её номером в блоке «Медиа»: шестая — плитка первого раздела, седьмая — второго. Считать порядок было мучением, поэтому перешли на ключи; перенос старых картинок делает `scripts/setup-banner.js` — он заполняет пустые ключи из первых пяти картинок и не трогает уже выбранное.

Шапка на компьютере — ряд разделов слева, логотип по центру, значки справа (`modules/layout/components/desktop-menu`). Пункт «Каталог» — обычная ссылка на весь каталог; при наведении под ним раскрывается панель во всю ширину: колонки ссылок и снимок справа (ключ `середина`). Панель закрывается с задержкой в 0,12 с, иначе схлопывалась бы, пока курсор идёт от кнопки к ней. Наведение на «Новинки» и «Скидки» её закрывает. Выезжающая шторка и поиск слева остались только на телефоне. Шторка на телефоне — белая во весь экран (`modules/layout/components/side-menu`). Каждая строка ведёт в сам раздел: нажал «Брюки» — увидел все брюки, а не список подразделов; подразделы есть на самой странице раздела, лишний промежуточный экран только задерживал. Ниже снимок со ссылкой на новинки, а кабинет, корзина и выбор языка — в самом низу и мельче: они нужны реже, чем каталог, ради которого меню и открывают.

Ссылок на несуществующие страницы в меню нет: как появятся «о бренде», «доставка», «возврат» — добавить их третьей колонкой в `templates/nav`.

Страница раздела показывает товары и всех его подразделов: в «Брюках» товаров нет, они лежат в «Прямых», «Зауженных» и «Широких», и без этого раздел верхнего уровня оказывался пустым.

Пункт «Скидки» ведёт в коллекцию `skidki` — она заведена в админке (**Товары → Коллекции → Скидки**) и пока пуста. Товар попадает туда галочкой в его карточке.

Полоса с акцией на компьютере уезжает вверх, как только страницу прокрутили, и возвращается при подъёме к самому верху (`modules/layout/components/promo-bar`); на телефоне остаётся на месте. Ширина, с которой считаем «компьютер», — 1024 px. Положение пересчитывается раз на кадр, а не на каждое событие прокрутки. Пороги разные — прячем после 48 px, показываем ниже 12: с одним общим полоса мигала бы, стоя ровно на нём. Начальное состояние не вычисляется: браузер восстанавливает прокрутку при обновлении страницы уже после запуска этого кода, из-за чего полоса пропадала сразу при заходе.

Блоки главной появляются при прокрутке: `modules/common/components/reveal` — всплывают на 24 px и проявляются за 0,7 с, каждый по разу. Первый экран не анимируется, он и так виден. При системной настройке «уменьшить движение» анимация выключается целиком.

Если запись удалить, витрина покажет запасные файлы из `apps/storefront/public/`.

## Справочные страницы

Лежат в `apps/storefront/src/app/[countryCode]/(main)/`, общая раскладка — `modules/content/components/page-layout`.

| Адрес | Страница | Видна |
|---|---|---|
| `/o-brende` | О бренде | всегда |
| `/dostavka` | Доставка | всегда |
| `/oplata` | Оплата | всегда |
| `/vozvrat` | Возврат и обмен | всегда |
| `/politika` | Политика обработки персональных данных | только с реквизитами |
| `/oferta` | Публичная оферта | только с реквизитами |

Юридические страницы открываются, лишь когда в админке заполнены реквизиты продавца — ключи `юр_наименование`, `юр_инн`, `юр_огрн`, `юр_адрес`, `юр_почта` в записи «Оформление сайта». Без них страница отдаёт 404, а ссылки в подвале не показываются: документ без наименования, ИНН и адреса оператора юридической силы не имеет, а публиковать пустой бланк — вводить покупателя в заблуждение. Заполнили — страницы и ссылки появляются сами.

Тексты оферты и политики написаны по общим правилам розничной торговли, закону о защите прав потребителей и 152-ФЗ, **но это не заменяет юриста**: перед запуском продаж их нужно вычитать под конкретное юрлицо.

Страницы «Доставка» и «Оплата» описывают то, как система устроена: расчёт нескольких служб при оформлении, двухстадийная оплата с заморозкой, чек по 54-ФЗ. Конкретных цен и сроков там намеренно нет — они считаются при оформлении и зависят от адреса.

## Оформление заказа

Одна страница вместо четырёх шагов: адрес, доставка, оплата и проверка видны сразу, кнопок «перейти к…» между ними нет.

Что из этого следует в коде (`modules/checkout/components/*`):

- у каждого раздела `isOpen = true` — прежние шаги жили в параметре `?step=` и сворачивали всё, кроме текущего;
- **адрес сохраняется сам**, когда все обязательные поля заполнены и покупатель ушёл из последнего: без этого пришлось бы жать кнопку ради того, чтобы ниже посчиталась доставка. Отправляем только при изменениях — иначе каждый переход между полями слал бы запрос;
- **платёжная запись заводится сама**, как только выбран способ оплаты: раньше это делала кнопка «перейти к проверке», а без записи не появляется кнопка «Оформить заказ».

Кнопка оформления одна, внизу, в блоке проверки.

Порядок: **город** → **доставка** → **данные получателя** → **оплата**.

Поле города — с подсказками: набрал «мо» — выпадают Москва, Московский, Можайск и прочие. Список лежит файлом `apps/storefront/src/lib/data/cities.json` (579 городов, 27 КБ) и собран скриптом `scripts/collect-cities.js` из самих пунктов выдачи ApiShip — это города, куда действительно возят, а не все населённые пункты страны. Своего справочника городов у ApiShip нет: есть только по отдельным службам, и Яндекса среди них нет.

Города отсортированы по числу пунктов, поэтому в подсказках сверху оказываются крупные. Список статический, поэтому подсказки мгновенные и не зависят от чужого сервиса; пересобирать — при добавлении новой службы доставки.

Отдельного блока с адресом нет. Проверено на живом расчёте: цена с одним городом, с индексом и с полной улицей совпадает до копейки, а без телефона и имени считается так же. Поэтому наверху одно поле «Город доставки» (`components/city-field`, страна проставляется сама), а контакты спрашиваются уже после того, как человек увидел цены и сроки. Улицу нужно будет спрашивать только у тех, кто выберет курьера, — этого пока нет.

В блоке получателя: фамилия, имя, почта, телефон плюс необязательные дата рождения и комментарий.

Оба блока пишут в один заказ, поэтому сохраняют через `updateCheckoutFields` (`lib/data/cart.ts`) — она подмешивает присланные поля к тем, что уже лежат в заказе. Обычное сохранение заменяет адрес целиком, и блоки затирали бы поля друг друга: контакты стирали бы улицу, адрес — почту.

Разделительных линий между блоками нет: на одностраничном оформлении они дробят его на куски.

## Карточка товара

На телефоне всё идёт сверху вниз: хлебные крошки, листалка фотографий, название, цена, описание, цвет, размеры, кнопка. Снимок в листалке занимает 92 % ширины — край следующего выглядывает справа, чтобы было видно, что фото не одно.

На компьютере два столбца: слева фотографии, справа сведения, прилипшие к верху — кнопка «в корзину» остаётся на виду, пока листаешь снимки. Раньше столбца было три (сведения слева, фото в середине, кнопки справа), и читать приходилось зигзагом.

Ширина фотографий — 38 % окна, по замерам референса. Половина, как было сначала, давала снимок почти в полтора экрана высотой: кадр 2:3 на широком мониторе растёт быстрее, чем кажется.

Прилипающей панели с кнопкой внизу экрана на телефоне больше нет: она закрывала фотографии и дублировала то, что и так рядом.

Кадр 2:3 — тот же, что в карточках каталога, чтобы товар не «прыгал» при переходе из списка.

Под кнопкой «В корзину» стоит «Купить сейчас» — та же покупка, только без остановки в корзине: вещь кладётся и покупатель сразу попадает к оформлению. На телефоне кнопки встают друг под друга, в строку не помещаются.

Размеры набраны текстом в строку, выбранный подчёркнут: рамки вокруг каждого делали из простого ряда цифр подобие клавиатуры. Рост остался вертикальной мерой с засечками.

Чего в карточке нет, хотя есть у референса: ссылки «таблица размеров» и строчки про бесплатную доставку. Первой нет страницы, вторая — обещание, а условия доставки ещё не решены. Появятся — добавим.

Цена стоит под названием, а не в блоке с размерами: покупатель видит её сразу, до всяких выборов. Если размеры товара стоят по-разному, к цене добавляется «от», а точная цена выбранного размера показывается ещё раз рядом с кнопкой. Когда цены одинаковы — а так обычно и есть — второго показа нет.

## Резервное копирование

Каждую ночь в 03:30 UTC снимаются копии базы (хранятся 14 дней) и фотографий товаров (последние 3 архива) в `/var/backups/volento/`. Фотографии копируются отдельно не зря: в дампе базы лежат только ссылки на файлы, и без архива снимков восстановленный магазин будет с пустыми карточками.

```bash
systemctl list-timers volento-backup    # когда следующий запуск
/usr/local/bin/volento-backup.sh        # снять копию прямо сейчас
ls -lh /var/backups/volento/            # что уже есть
```

Восстановление из копии:

```bash
. /root/.volento-secrets
sudo -u postgres createdb -O volento volento_restore
gunzip -c /var/backups/volento/volento_ГГГГ-ММ-ДД_ЧЧ-ММ.sql.gz \
  | PGPASSWORD="$DB_PASSWORD" psql -h 127.0.0.1 -U volento -d volento_restore
```

Восстанавливать сначала в отдельную базу, посмотреть, что данные на месте, и только потом заменять рабочую. Проверка восстановления делалась — дамп разворачивается полностью.

## Шрифты

Лежат в `apps/storefront/public/fonts/` и подключены в `src/styles/fonts.css` — с Google не тянутся: внешняя зависимость один раз уже уронила сборку, да и покупателям незачем ходить на чужие домены.

Сейчас весь сайт набран **Jost** — геометрический гротеск. Рядом лежат и подключены ещё два комплекта — **Tenor Sans** и **Lora** (антиква с засечками): примерить любой — это убрать лишние имена из двух переменных в `globals.css`, заново качать ничего не надо. Все под SIL OFL, копии лицензий рядом с файлами.

Важное различие: Jost и Lora переменные, насыщенности в них настоящие — `font-light`, `font-medium`, `font-bold` работают честно. У Tenor Sans начертание одно, поэтому «сделай легче» на нём не даёт ничего, а «сделай жирнее» браузер подделает грубым скачком.

Файл разбит по алфавитам, браузер тянет только нужные куски:

| Файл | Что покрывает | Размер |
|---|---|---|
| `tenor-sans-cyrillic.woff2` | русский | 6 КБ |
| `tenor-sans-latin.woff2` | латиница | 10 КБ |
| `tenor-sans-latin-ext.woff2` | расширенная латиница | 7 КБ |
| `jost-cyrillic.woff2` | русский | 10 КБ |
| `jost-latin.woff2` | латиница | 26 КБ |
| `jost-latin-ext.woff2` | расширенная латиница | 17 КБ |
| `lora-cyrillic.woff2` | русский, запасной комплект | 21 КБ |
| `lora-cyrillic-ext.woff2` | остальная кириллица | 23 КБ |
| `lora-latin.woff2` | латиница | 37 КБ |
| `lora-latin-ext.woff2` | расширенная латиница | 20 КБ |

Неиспользуемый комплект браузер не скачивает: правило `@font-face` тянет файл только когда шрифт реально понадобился.

Роли задаются переменными в `src/styles/globals.css`: `--font-display` (заголовки) и `--font-sans` (текст) — сейчас обе указывают на Jost, следом Tenor Sans и Lora запасными. Размер заголовков главной — в одном месте, `modules/home/components/section-heading`.

Прежние Doloman Pavljenko, Prata и Manrope удалены: они больше нигде не использовались, а мёртвые файлы в раздаче только путают.

## Скрипты

| Скрипт | Что делает |

| `seed-test-catalog.js` | Тестовый каталог: модели, цвета, фотографии, остатки |
| `build-catalog.py` | Готовит `catalog.json` из складской выгрузки `.xlsx` |

| `check-checkout.js` | Проверка связей корзины с доставкой и оплатой — то, что ломается при конфликте версий `@mikro-orm` |
| `collect-cities.js` | Собирает справочник городов из пунктов выдачи ApiShip в `apps/storefront/src/lib/data/cities.json` |

## Переменные окружения

`apps/backend/.env` — значения смотреть на сервере, здесь только имена:

```
NODE_ENV, DATABASE_URL, REDIS_URL, EVENTS_REDIS_URL, WE_REDIS_URL, CACHE_REDIS_URL,
JWT_SECRET, COOKIE_SECRET, AUTH_MFA_ENCRYPTION_KEY,
STORE_CORS, ADMIN_CORS, AUTH_CORS
```

Redis разделён по базам: `/0` сессии, `/1` события, `/2` движок процессов, `/3` кеш.

`WORKER_MODE` и `ADMIN_DISABLED` в `.env` не задаются — их выставляют systemd-юниты, чтобы один и тот же код работал и как сервер, и как воркер.

`apps/storefront/.env.local`:

```
NEXT_PUBLIC_MEDUSA_BACKEND_URL, NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY,
NEXT_PUBLIC_BASE_URL, NEXT_PUBLIC_DEFAULT_REGION,
VITRINA_KLYUCH  (серверная, см. «Магазин закрыт до открытия»)
```

`DADATA_KEY` (серверная, необязательная): «API-ключ» из личного кабинета dadata.ru, по нему поле «Город доставки» ищет посёлки и деревни (`lib/data/poselki.ts`). Без ключа ищутся только города из `cities.json`. Бесплатно — 10 000 подсказок в день. Город посёлку подбирается по ближайшему пункту выдачи из `punkty-vydachi.json`: его вместе с `cities.json` обновляет `scripts/collect-cities.js`.

Все переменные витрины с приставкой `NEXT_PUBLIC_` попадают в код, который выполняется в браузере покупателя. Поэтому `NEXT_PUBLIC_MEDUSA_BACKEND_URL` — это публичный адрес `https://api.slytn.ru`, а не внутренний `127.0.0.1:9000`. Секреты в переменные с такой приставкой класть нельзя.

## Структура каталога

Заложена сознательно, менять осторожно:

- **Товар** — модель определённого цвета, со своим артикулом (например, «Брюки классические прямые, чёрный», артикул `VLT-001-BLK`).
- **Вариант** — размер + рост. У каждого свой SKU.
- **SKU** — формат `АРТИКУЛ-РАЗМЕР-РОСТ`, например `VLT-001-BLK-46-170`. Должен совпадать со складским посимвольно: к нему будет привязана синхронизация остатков.
- **Остатки** ведутся на уровне варианта, на складе «Основной склад».
- Регион «Россия», валюта — рубль.

**Почему цвет — отдельный товар, а не опция варианта.** Каталог в Medusa перечисляет товары, а не варианты. Если бы цвет был опцией внутри товара, модель попадала бы в каталог одной карточкой, и показать её же в трёх цветах тремя карточками было бы нельзя. Плюс фотографии в Medusa привязаны к товару, а не к варианту — при переключении цвета снимки не менялись бы. И артикул со склада уже содержит цвет, иначе два цвета одной модели давали бы одинаковый SKU.

**Как цвета связаны между собой.** У каждого товара есть метка `model:<КОД МОДЕЛИ>` и поля `model`, `article`, `color`, `color_hex` в metadata. Компонент `ColorSelect` на витрине находит по метке остальные цвета модели и рисует переключатель.

Метку и поля заполняет импорт из выгрузки, руками их трогать не нужно.

## Импорт каталога из выгрузки склада

Два шага. Первый готовит данные на компьютере, второй заводит их на сервере.

```bash
# 1. из .xlsx получаем catalog.json
python3 scripts/build-catalog.py "data/warehouse/2026-09-02-ostatki.xlsx"

# 2. кладём на сервер и заводим
scp scripts/import-catalog.js scripts/catalog.json volento:/home/volento/
ssh volento 'sudo bash -c "set -a; . /root/.volento-secrets; set +a; cd /home/volento && node import-catalog.js"'
```

Полезные ключи `import-catalog.js`:

- `--limit 2` — только первые два товара, для пробы;
- `--stock` — не трогать товары, обновить одни остатки;
- `--price 5900` — поставить всем одну цену вместо заглушки.

Что делает `build-catalog.py`:

- берёт из выгрузки строки «Женское / Брюки»;
- группирует по артикулу склада: артикул = товар, строки внутри = варианты (размер + рост);
- **выдаёт свои коды** `VLT-0001`, SKU варианта `VLT-0001-46-170`. Складской артикул не годится в SKU: он чужой и может поменяться, поэтому лежит в `metadata.article`, а ключ синхронизации `артикул-размер-рост` — в `metadata.wh_key` каждого варианта;
- берёт номер модели из «Мод. NNN» в названии (он есть у всех строк) и ставит метку `model:NNN` — по ней собирается переключатель цветов;
- **собирает название заново.** В выгрузке названия складские: имена поставщиков («Зара», «Оле Доле», «Elie Saab», «Charmstore»), коды тканей («D#13», «GC8369-9»), номера цветов. Ставить это на витрину нельзя, поэтому название складывается из кроя и ткани: «Брюки палаццо изо льна, бежевый». Исходное имя сохраняется в `metadata.source_name`;
- остаток берёт из колонки «Доступный запас», а не из физического.

Правила разбора — списки `FABRIC` (ткань) и `CUT` (крой) в начале скрипта. Появится новая модель или ткань — дописать туда, иначе название соберётся без этой части.

Импорт **можно запускать повторно**: товар с уже занятым адресом пропускается, остатки обновляются.

**Товары заводятся черновиками.** В выгрузке склада нет колонки с ценой, а Medusa не создаёт вариант совсем без цены. Поэтому ставится заглушка 1 ₽ и `metadata.price_pending = true`. Черновик не виден на витрине и не покупается — продать по 1 ₽ нельзя. Перед публикацией цены нужно проставить.

## Оплата: сертификат Минцифры

Сертификат `tochka.com` выдан корневым центром Минцифры, которого нет в
доверенных ни у macOS, ни у Node. Без него любой запрос к API банка падает
с `SELF_SIGNED_CERT_IN_CHAIN`, а curl отдаёт код 000 — выглядит как «сайт
недоступен», хотя дело в доверии, а не в сети.

Связка лежит в `deploy/certs/tochka-ca.pem` (корневой + промежуточный,
скачаны с gu-st.ru). На сервере она в `/etc/volento/tochka-ca.pem` и
прописана **только нашему бэкенду** — дополнением к юнитам
`medusa-server` и `medusa-worker`:

```
/etc/systemd/system/medusa-server.service.d/tochka-ca.conf
[Service]
Environment=NODE_EXTRA_CA_CERTS=/etc/volento/tochka-ca.pem
```

В общесистемное хранилище не добавляли специально: иначе серверу пришлось
бы доверять этому центру целиком. Откат — удалить два файла-дополнения и
`systemctl daemon-reload`.

Проверка (с сервера, из-под пользователя volento):

```bash
NODE_EXTRA_CA_CERTS=/etc/volento/tochka-ca.pem node -e '
fetch("https://enter.tochka.com/sandbox/v2/open-banking/v1.0/customers",
 {headers:{Authorization:"Bearer sandbox.jwt.token"}}).then(r=>console.log(r.status))'
```

Должно быть 200. Без токена — 403, тоже нормально: значит TLS прошёл.

Промежуточный сертификат истекает в марте 2027 — перевыпустить связку.

## Особенности, о которых стоит помнить

**Витрина вне общего пространства зависимостей.** Стартер Medusa рассчитан на pnpm; при установке через npm зависимости «поднимаются» в корень, и Next начинает видеть React 18 от бэкенда вместо React 19. Сборка падает с React error #31. Поэтому `apps/storefront` исключён из `workspaces` в корневом `package.json` и имеет собственный `node_modules`. Не возвращайте его в workspaces без перехода на pnpm.

**Патч в `apps/storefront/src/middleware.ts`.** За обратным прокси Next не доверяет заголовку `Host` и подставляет `localhost:8000`, из-за чего покупатель уезжает на несуществующий адрес. Origin для перенаправления собирается из заголовков `x-forwarded-host` / `host`, которые проставляет nginx. При обновлении стартера патч нужно накатить заново.

**Откуда берётся витрина.** Из официального шаблона `medusajs/dtc-starter` — это тот же монорепозиторий, из которого `create-medusa-app` разворачивает бэкенд. Отдельный репозиторий `medusajs/nextjs-starter-medusa` заархивирован в июле 2026 и больше не обновляется; брать код оттуда не надо.

**Сборка витрины обращается к API по публичному адресу.** `NEXT_PUBLIC_MEDUSA_BACKEND_URL` попадает в браузерный код, поэтому там публичный `https://api.slytn.ru` — и при сборке сервер стучится сам к себе через внешний интерфейс. Такая петля ненадёжна и один раз уронила сборку по таймауту. В `/etc/hosts` на сервере добавлено `127.0.0.1 api.slytn.ru`, чтобы запросы шли сразу на локальный nginx. На браузеры покупателей это не влияет.

**Не пересобирайте витрину одновременно с изменением каталога.** Сборка собирает данные страниц из API; если в этот момент товары пересоздаются, сборка падает.

**Перевод витрины.** Русский текст вписан прямо в компоненты, библиотеки локализации нет — магазин одноязычный, и лишний слой абстракции тут не нужен. Обратная сторона: при обновлении витрины из upstream переводы придётся накладывать заново. Формат цен и дат задаётся локалью `ru-RU` в `src/lib/util/money.ts` и в местах вывода дат.

**Кеш витрины.** Витрина (Next.js) запоминает товары, цены, наличие и картинки главной. Всё запомненное помечено общей меткой `vitrina` (`apps/storefront/src/lib/data/cookies.ts`). Правки в админке сбрасывают её сами: подписчик `subscribers/obnovit-vitrinu.ts` ловит изменения товаров, размеров, разделов, коллекций и остатков, а ручка склада `/sklad/ostatki` зовёт сброс напрямую (модуль остатков событий не шлёт). Через 3 секунды затишья бэкенд забывает свою память (`/store/v-nalichii`, `/store/ceny-sortirovka`) и зовёт витрину `POST /api/obnovit`. Обе стороны проверяют общий ключ `OBNOVIT_KEY`: он лежит в `apps/backend/.env` и `apps/storefront/.env.local`. Код — `apps/backend/src/lib/pamyat-vitriny.ts`.

Раньше метка была привязана к куке посетителя, а у посетителя без куки её не было вовсе: запомненное жило до перезапуска, и картинки главной из админки не появлялись.

Если что-то всё же застряло, сбросить вручную:

```bash
rm -rf /home/volento/volento/apps/storefront/.next/cache
systemctl restart volento-storefront
```

## Доставка: ApiShip

Доставку считает и оформляет [ApiShip](https://apiship.ru) — агрегатор служб: одна интеграция, а внутри СДЭК, Почта России, Boxberry, Яндекс Доставка, СберЛогистика, ПЭК и ещё три десятка. Договоры магазин заключает **напрямую с перевозчиками**, ApiShip только передаёт данные и денег через себя не пропускает; базовые методы бесплатны.

Плагин — [`@gorgo/medusa-fulfillment-apiship`](https://www.npmjs.com/package/@gorgo/medusa-fulfillment-apiship) (MIT). Умеет расчёт стоимости по габаритам и весу, выбор пункта выдачи списком и на карте, создание отправления из админки в один клик, печать этикеток и накладных, тестовый режим.

Ключ ApiShip **не в конфиге**, а в админке: **Настройки → Интеграции → ApiShip**. Секреты там шифруются, связь проверяется до сохранения. За это отвечает модуль `@gorgo/medusa-integration`; ему нужна переменная `INTEGRATION_ENCRYPTION_KEY` — она заведена в `.env` бэкенда, без неё настройки не расшифровать.

Витрине для карты пунктов выдачи нужен ключ Яндекс.Карт (`NEXT_PUBLIC_YANDEX_MAPS_API_KEY`) и обязательный телефон в адресе доставки — ApiShip без телефона не считает.

Адреса пунктов выдачи запрашиваются **порциями по 150 номеров** (`lib/data/fulfillment.ts`). В примере авторов они спрашиваются одним запросом, а в Москве пунктов тысячи: адрес запроса вырастал до десятков тысяч знаков, и nginx отвечал `Request-URI Too Large` — карта открывалась пустой с надписью «пунктов не нашлось».

**У варианта доставки обязана быть строка цены — даже когда цена считается перевозчиком.** У «Пункта выдачи» (`price_type: calculated`) цены однажды пропали, и оформление встало намертво: вариант серый с прочерком вместо цены, нажать нельзя, карта не открывается. В логах витрины — `Shipping options with IDs so_… do not have a price`. Лечится строкой с нулём:

```bash
curl -s -X POST "http://localhost:9000/admin/shipping-options/<ID варианта>" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"prices":[{"currency_code":"rub","amount":0}]}'
```

Ноль тут — заглушка: настоящую цену отдаёт ApiShip при расчёте. Проверить, что цены на месте: `GET /admin/shipping-options?id=<ID>&fields=*prices`. Стоит смотреть после любой правки варианта доставки в админке.

Осторожно: плагин в бете (2.0.0-beta.5), версия закреплена жёстко. У авторов есть чат поддержки в телеграме — @gorgojs_chat.

**Заплатка в `scripts/build-backend.sh`.** В админке плагина список «Пункт приёма заказов» запрашивается без фильтра по городу (в их исходниках фильтр закомментирован), а на сервере стоит предел в 50 записей. ApiShip отдаёт полсотни случайных точек по всей стране: в списке Тверь и Йошкар-Ола, а московских — четыре. Сборка дописывает город прямо в запрос; город берётся из `APISHIP_CITY`, по умолчанию Москва.

Заплатка временная и намеренно нежёсткая: если в новой версии плагина строка изменится, правка просто не применится, сборка напишет предупреждение и продолжится. Как починят — заплатку убрать.

### Один заказ — несколько пакетов

Склад может разделить заказ на пакеты: в «собрано» вместо `pozicii`
шлёт `pakety` (docs/СКЛАД-API.md, раздел 4). В службу уходит одно отправление из
стольких же мест: одна цена, один трек. Наклейка — на каждый пакет
(`/etiketka?paket=N`), «упаковано» можно отмечать по пакетам.

- Логика: `apps/backend/src/lib/sklad-pakety.ts`; заявка в ApiShip —
  `modules/dostavka-apiship/service.ts`.
- **Размеры и вес посылки — одна таблица:**
  `apps/backend/src/lib/upakovka-tablica.ts`. Замеров от склада пока нет:
  места считаются стопкой из размеров в карточках товаров, как раньше.
  Придут замеры — вписать строки в `pakety` этого файла, больше нигде
  править не надо.
- Заказ в постамат делить нельзя (склад получит `409`).
- Наклейку по страницам делит библиотека `pdf-lib`. Она записана в
  `apps/backend/package.json`; в собранную папку её ставит сама сборка.
  В корневой `node_modules` на сервере она положена вручную (нужна
  только сборке, чтобы та видела типы).
- Проверить заявку из двух мест в ApiShip, ничего не создавая:
  `cd apps/backend/.medusa/server && npx medusa exec ./src/scripts/proverka-mest.js`
  (с переменными из `.env`). В журнале строки «[места] … valid: true».
- Что не проверено вживую: настоящего отправления из двух мест ещё не
  было. Порядок страниц в наклейке службы (страница N = место N) взят из
  документации; если страниц окажется не столько, сколько мест, склад
  получит файл целиком и заголовок `X-Nakleyka: vse-mesta`.

## Магазин закрыт до открытия

Пока магазин не открыт, посторонний не должен суметь оформить и оплатить заказ. Закрыто в два слоя.

**Пароль на витрине.** nginx спрашивает логин и пароль на `slytn.ru` и `www` (`auth_basic`, файл `/etc/nginx/.htpasswd-volento`). Логин и пароль лежат в `/root/.volento-secrets` (`VITRINA_LOGIN`, `VITRINA_PAROL`). `api.slytn.ru` и `admin.slytn.ru` не закрыты: туда ходят склад и вебхук банка.

**Замок заказов в бэкенде** (`apps/backend/src/lib/zamok-zakazov.ts`). Одного пароля мало: API открыт всему миру, а `/store` проксируется ещё и через админский домен. Пока `ZAKAZY_OTKRYTY` не равен `true`, три действия разрешены только запросу с заголовком `x-vitrina-klyuch`, равным `VITRINA_KLYUCH`:
- оформить корзину (`/store/carts/:id/complete`);
- начать оплату (`/store/payment-collections/:id/payment-sessions`);
- маршруты `/store/oplata/*`.

Всем остальным замок отвечает 403 «Магазин ещё не открыт». Ключ знает только сервер витрины. Он лежит в обоих `.env` под одним именем `VITRINA_KLYUCH`, без `NEXT_PUBLIC_`, и подставляется в `lib/config.ts` только на сервере.

**Пробные заказы.** Всё, что оформлено при закрытом магазине, получает `metadata.test = true`. Medusa переносит метаданные корзины в заказ. Такие заказы не попадают складу в `/sklad/zadaniya`, и сторож «склад молчит» о них не пишет.

### Открытие магазина

1. В `apps/backend/.env` дописать `ZAKAZY_OTKRYTY=true` и перезапустить `medusa-server` и `medusa-worker`. Пересборка не нужна, переменная читается при каждом запросе.
2. Убрать из `/etc/nginx/sites-available/volento` строки `auth_basic` и `auth_basic_user_file`, затем выполнить `nginx -t && systemctl reload nginx`. То же сделать в `deploy/nginx/volento.conf`.
3. `ALLOW_INDEXING=true` в `.env.local` витрины, затем пересобрать и перезапустить её.
4. Удалить скрытый товар для проверки оплаты: `node scripts/tovar-proverka.js --udalit` (логин админки — из `/root/.volento-secrets`).

## Оплата: эквайринг Точки

Основа — готовый плагин [`medusa-payment-tochka`](https://www.npmjs.com/package/medusa-payment-tochka) (MIT, Medusa 2.7+). Подключён не напрямую, а через наш провайдер `apps/backend/src/modules/oplata-tochka`, который наследует плагин. Поправки:

- **Карта и СБП.** У плагина способ оплаты зашит, и это только карта.
- **Сумма.** Medusa передаёт сумму объектом, а плагин превращал её в `NaN`. Приводим её к числу сами.
- **Сверка перед оформлением заказа.** Плагин верил любому ответу «оплачено». Мы проверяем, что номер операции совпал с нашим и оплачено не меньше суммы заказа, иначе заказ не оформится. В песочнице расхождение только пишется в журнал: она всегда отвечает «оплачено 100 ₽» по чужой операции.
- **Код клиента и торговая точка** берутся из настроек, а не ищутся при каждом платеже.
- **Разбор уведомления.** Тело берётся и из `data`, и из сырого тела запроса. Точка шлёт голый JWT с типом `text/plain`.

**Как идёт оплата.**
1. Кнопка «Оплатить» на витрине вызывает `POST /store/oplata/tochka`. Маршрут сам читает корзину из базы, заново проверяет наличие и отдаёт ссылку на страницу банка. Повторное нажатие в течение 45 минут отдаёт ту же ссылку, чтобы у покупателя не было двух живых платежей.
2. Банк возвращает покупателя на `/checkout/oplata?cart=…`. Страница несколько раз спрашивает, подтверждена ли оплата, и оформляет заказ.
3. Если покупатель закрыл вкладку, заказ оформится по уведомлению банка: `https://api.slytn.ru/hooks/payment/tochka_tochka`.

**Чеков Точка не формирует** (`withReceipt` не задан). Все товары маркированы «Честным знаком», а код маркировки знает только склад при сборке. В чеке Точки поля для кода нет вовсе (проверено по её OpenAPI), поэтому чеки выбивает наш код через Атол Онлайн — см. «Касса: Атол Онлайн». Касса Атол привязана к торговой точке и в кабинете Точки, но по ссылке без чека Точка её не трогает.

**Коды маркировки и неполная сборка.**
- Склад присылает коды в `POST /sklad/zadaniya/:nomer/sborka`. Они лежат в заказе, в `metadata.kody_markirovki` (строка заказа и список кодов к ней). По ним выбивается чек «полный расчёт».
- Если склад собрал не всё, заказ получает `metadata.sklad_nehvatka`, а на `EMAIL_TREVOGA` и в колокольчик админки приходит «позвоните покупателю». В карточке заказа появляются две кнопки: «Отправить остаток» (заказ урезается, за недостающее возвращаются деньги, собранное уходит в службу) и «Отменить заказ».
- Плагин ApiShip подключён через поправку `src/modules/dostavka-apiship`. Первое: в службу уходит только собранное, а сам плагин кладёт в посылку весь заказ. Второе: в отправление уходит оценочная стоимость — настоящая цена вещей. Плагин ставил 0, и посылка была без страховки. Страховка у Яндекса — 0,5% от оценки.
- Размер наклейки задаётся в кабинете ApiShip, в настройках подключения службы.
- Тестовые заказы склада: `POST /sklad/proba/zakaz` (`lib/sklad-test.ts`). Оплачены без банка, позиции без товара из каталога, в службу ничего не уходит. Видны только в `/sklad/zadaniya?test=1` и `/sklad/k-upakovke?test=1`. Папку маршрута нельзя называть `test`: сборка Medusa такие папки пропускает.

Провайдер подключается, **только когда задан `TOCHKA_JWT_TOKEN`**. Переменные в `apps/backend/.env`:

| Переменная | Что это |
|---|---|
| `TOCHKA_JWT_TOKEN` | токен из интернет-банка Точки; в песочнице `sandbox.jwt.token` |
| `TOCHKA_CLIENT_ID` | идентификатор приложения там же |
| `TOCHKA_CUSTOMER_CODE` | код клиента (юрлица) в Точке; если не задан, плагин ищет его сам |
| `TOCHKA_MERCHANT_ID` | номер торговой точки интернет-эквайринга; банк требует его, если точек несколько |
| `TOCHKA_WEBHOOK_PUBLIC_KEY` | открытый ключ Точки для проверки уведомлений, JSON в одну строку в одинарных кавычках. Берётся с `https://enter.tochka.com/doc/openapi/static/keys/public` |
| `TOCHKA_DEVELOPER_MODE` | `true` — песочница |
| `TOCHKA_PREAUTH` | `true` включает двухстадийную оплату; по умолчанию выключена |
| `VITRINA_URL` | куда банк возвращает покупателя, по умолчанию `https://slytn.ru` |

**Сейчас на сервере боевой режим** (с 1 октября 2026). Деньги настоящие, но магазин закрыт паролем и замком заказов. Боевые токен и client_id лежат также в `/root/.tochka-boevye`.

Чтобы вернуться в песочницу, задайте `TOCHKA_JWT_TOKEN=sandbox.jwt.token`, `TOCHKA_DEVELOPER_MODE=true`, `TOCHKA_CUSTOMER_CODE=1234567ab`, `TOCHKA_MERCHANT_ID=200000000001097` и перезапустите `medusa-server` и `medusa-worker`. Песочница всегда отвечает «оплачено 100 ₽» по чужой операции, а вместо страницы оплаты отдаёт несуществующий `merch.example.com`.

**Адрес для уведомлений** зарегистрирован в Точке через API: `PUT /uapi/webhook/v1.0/{client_id}`, событие `acquiringInternetPayment`, адрес `https://api.slytn.ru/hooks/payment/tochka_tochka`. Пробное уведомление отправляется через `POST …/{client_id}/test_send`. Его подпись проверяется, но операция в нём выдуманная, поэтому в журнале будут ошибки `retrievePayment` и три повтора. Это нормально.

**Способ оплаты в регионе.** `scripts/oplata-region.js` оставляет в рублёвом регионе только Точку и убирает «Оплату вручную». С флагом `--proverka` скрипт только показывает текущее состояние. Запуск: `set -a; . /root/.volento-secrets; set +a; node scripts/oplata-region.js`.

Двухстадийная оплата пока **выключена**: деньги списываются сразу. Включается переменной `TOCHKA_PREAUTH=true`.

Плагину нужен сертификат Минцифры (см. раздел выше), он лежит в `/etc/volento/tochka-ca.pem`. Проверять доступ к Точке с сервера: `curl --cacert /etc/volento/tochka-ca.pem …`.

Осторожно: плагин версии 0.1.x, автор один, проверялся с Medusa 2.10, а у нас 2.18. Версия закреплена жёстко, обновлять только с проверкой в песочнице.

Отдельная грабля: в зависимостях плагина `@mikro-orm` закреплён ровно на 6.4.3, а Medusa 2.18 работает на 6.6. При установке внутрь собранной папки npm ставил старую версию, и сервер поднимался с поломанными связями модулей: корзина не находила оплату, доставка не находила тарифы, в журнале было `Cannot read properties of undefined (reading 'className')`. Поэтому `scripts/build-backend.sh` перед установкой дописывает жёсткое закрепление `@mikro-orm` на версию самой Medusa.

## Касса: Атол Онлайн

Код — `apps/backend/src/lib/kassa.ts`, протокол Атола v5 (ФФД 1.2). Документация — PDF «API сервиса АТОЛ Онлайн_v5» из кабинета Атола.

**Какие чеки и когда.**

| Когда | Чек | Откуда вызывается |
|---|---|---|
| заказ оформлен и оплачен через Точку | «Предоплата 100 %», без кодов, НДС 5/105 | `subscribers/kassa-predoplata.ts` |
| служба выдала посылку (статус ApiShip) | «Полный расчёт» только на забранные пары: по позиции на каждую с её кодом, зачёт предоплаты, НДС 5 % | `lib/dostavka-itog.ts`, `подвестиИтог` |
| покупатель забрал не всё (или ничего) | деньги за незабранное обратно через Точку и «Возврат предоплаты» на него | `lib/dostavka-itog.ts` |
| «Отправить остаток» в админке | «Возврат предоплаты» за недостающее | `lib/sklad-ostatok.ts` |
| заказ отменён | «Возврат предоплаты» за всё, что не закрыто расчётом | `subscribers/kassa-otmena.ts` |

Доставка идёт отдельной позицией (услуга) и закрывается первым же расчётом. Покупатель не забрал ничего — расчёт только на доставку: её служба оказала, деньги за неё не возвращаем.

**Примерка и частичный выкуп** (исследование — `docs/примерка-и-частичный-выкуп.md`).
- Витрина показывает только пункты с примерочной (`fittingRoom=1`); если у службы в городе таких нет — все её пункты с пометкой «Без примерочной».
- При создании отправления (`modules/dostavka-apiship`) каждая пара уходит отдельной строкой со своим кодом ЧЗ (`markCode`), а службе заказывается частичный выкуп: Яндексу `yataxi.particular_items_refuse` (только в пункт с примерочной), СДЭК `cdek.PartialDelivery`. Служба не приняла заказ с этой услугой — уходит без неё, приходит тревога «ушёл без примерки».
- Сторож `jobs/dostavka-statusy.ts` раз в 15 минут спрашивает ApiShip статусы упакованных посылок. `delivered` — забрали всё, `partialReturn` — часть (по `quantityDelivered` каждой пары), `returnReady`/`returning`/`returned`/`returnedFromDelivery` — ничего. Итог пишется в `metadata.dostavka_itog` заказа по сборке, шаги отмечаются, повтор безопасен: деньги дважды не вернутся. `lost`/`problem` и посылка в пути дольше `DOSTAVKA_ZAVIS_DNEY` (21) — тревога, один раз.
- Склад видит, что едет назад, в `GET /sklad/vozvraty` и принимает возврат `POST /sklad/zadaniya/:nomer/vozvrat` с кодами пришедших пар. Не совпали с ожидаемыми — тревога: в чеке продан не тот код, правим вручную.
- Тестовые заказы «выдаёт» `POST /sklad/proba/vydacha/:nomer`; сценарии — `scripts/sklad-scenarii.sh`.

**Как уходит чек.** Сначала записывается в заказ, в `metadata.kassa_cheki`, потом отправляется. Номер чека для Атола постоянный (`volento-<номер заказа>-predoplata` и т. п.), поэтому дубль Атол не пробьёт. Сторож `jobs/kassa-cheki.ts` раз в 5 минут дотправляет то, что не ушло, и узнаёт результат. Чек пробит — в нём появляется `ssylka` на чек в ОФД. Атол отказал — статус `fail`, письмо на `EMAIL_TREVOGA` и колокольчик в админке.

Чеки бьются только по оплате через Точку. Тестовые заказы склада оплачены «системным» способом, по ним касса молчит.

**Возврат через кабинет** (`lib/vozvrat-pokupatelya.ts`, витрина — блок «Возврат» на странице заказа). Вернуть можно забранное, в течение `VOZVRAT_DNEY` (7) дней после выдачи до конца дня по Москве. Заявка — в `metadata.vozvraty_pokupatelya` заказа, покупателю письмо с инструкцией `VOZVRAT_INSTRUKCIYA` (не задана — «пришлём на почту, куда отправить», а Тимофею тревога с составом заявки). Склад видит заявку в `/sklad/vozvraty` (`vid: pokupatel`) и принимает кодами; `otkloneno` — пары, которые не принял. За принятые — возврат денег через Точку и чек «возврат прихода» с кодами (`planned_status` 3), по нему код возвращается в оборот ЧЗ. Ручки покупателя: `GET/POST /store/vozvrat/:id_заказа`, только свой заказ.

**Не автоматизировано:** отмена заказа, по которому уже был полный расчёт (то есть после выдачи) — возврат идёт через кабинет. Это возврат проданных вещей, коды надо вернуть в оборот — приходит тревога, чек делаем вручную.

**Переменные** в `apps/backend/.env`. Касса включается, когда заданы первые пять.

| Переменная | Что это |
|---|---|
| `ATOL_LOGIN`, `ATOL_PASSWORD`, `ATOL_GROUP_CODE` | из файла настроек интеграции в кабинете Атола (XML) |
| `ATOL_INN` | ИНН продавца, там же |
| `ATOL_PAYMENT_ADDRESS` | место расчётов — адрес сайта, на который зарегистрирована касса: `volento.com` |
| `ATOL_SNO` | система налогообложения, по умолчанию `usn_income` |
| `ATOL_VAT`, `ATOL_VAT_PREPAYMENT` | НДС в расчёте и в предоплате, по умолчанию `vat5` и `vat105` |
| `ATOL_EMAIL` | почта продавца в чеке, по умолчанию `none` |
| `ATOL_TSPIOT` | старый переключатель: `true` то же, что `KASSA_PROVERKA_KM=tspiot` |
| `ATOL_URL` | по умолчанию боевой `https://online.atol.ru/possystem/v5` |

**Проверка кодов в «Честном знаке»** (`lib/chz.ts`, подробно с источниками в `docs/честный-знак-без-тс-пиот.md`). Перед «полным расчётом» каждый код проверяется в ЧЗ, а факт и время проверки идут в чек: `sectoral_item_props` = `030`, `21.11.2023`, `1944`, `UUID=<reqId>&Time=<reqTimestamp>`. Код нельзя продавать (продан, не в обороте, чужой, заблокирован) — чек не бьётся, приходит тревога. ЧЗ не отвечает — чек ждёт, сторож пробует каждые 5 минут, через час тревога. Ответ 203 (авария в ЧЗ) — чек уходит без проверки.

| Переменная | Что это |
|---|---|
| `KASSA_PROVERKA_KM` | кто проверяет коды: `chz` — мы сами токеном ЧЗ (пока Атол не подключил ТС ПИоТ); `tspiot` — Атол через ТС ПИоТ (`use_tspiot`, `permissive_mode`); `net` — никто, только для тестов. Не задано: `tspiot` при `ATOL_TSPIOT=true`, иначе `chz`, если есть `CHZ_TOKEN`, иначе `net`. Действует в момент отправки, так что чеки из очереди тоже уйдут по новой схеме |
| `CHZ_TOKEN` | токен ЧЗ для кассы (X-API-KEY): кабинет ЧЗ, «Профиль», «Токен для контрольно-кассовой техники». Только в `.env`, не в git и не в чат: опубликованный токен ЧЗ блокирует |
| `CHZ_FN` | заводской номер фискального накопителя (16 цифр), необязательно: при подозрениях ЧЗ заблокирует одну кассу, а не весь токен |
| `CHZ_URL` | по умолчанию боевой `https://cdn.crpt.ru`; тестовый контур ЧЗ `https://markirovka.sandbox.crptech.ru` (нужен свой токен тестового контура) |
| `CHZ_TIMEOUT_MS` | сколько ждать ответа площадки, по умолчанию 3000 |
| `CHZ_TOLKO_SVOI` | `false` — разрешить продавать коды другого владельца. По умолчанию нельзя: это ошибка склада |

**Проверка без настоящих чеков.** У Атола есть тестовая касса `https://testonline.atol.ru/possystem/v5` с открытыми данными из его документации: логин `v5-online-atol-ru`, пароль `zUr0OxfI`, группа `v5-online-atol-ru_5179`, ИНН `5544332219`, место `https://v5.online.atol.ru`. Чтобы гонять на ней тестовые заказы склада, на время проверки задаётся `ATOL_LYUBAYA_OPLATA=true` — тогда чек бьётся по любой оплате. На бою эту переменную не задавать.

## Требования закона на сайте

Сверено 20 октября 2026 с законом о защите прав потребителей, правилами продажи (постановление 2463) и 152-ФЗ.

- **Продавец в подвале** каждой страницы: наименование, ИНН, ОГРНИП, адрес, почта. Берутся из админки, «Главная», поля `юр_*`.

- **Состав, ткань, страна, уход** в карточке товара: метаданные `sostav`, `tkan`, `strana`, `uhod`, правятся в админке в карточке товара. Заполнены 20 октября с Озона (атрибуты 4604, 4496, 4389, 4655) по артикулу.

| `EMAIL_REPLY_TO` | `info@volento.com` |
| `STOREFRONT_URL` | адрес витрины, для ссылки «посмотреть заказ» |
| `ZAKAZ_BEZ_VHODA` | `true` — пускать к оплате без входа (аварийный выключатель). По умолчанию заказ оформляет только вошедший покупатель: витрина просит войти по коду, сервер отказывает гостю (`lib/tolko-pokupatel.ts`). Покупателю вход только по коду (`authMethodsPerActor` в medusa-config), пароль — только админке |
| `E2E_KLYUCH` | ключ автотестов: с ним `/store/vhod` для адресов `@example.com` отдаёт код в ответе вместо письма. Не задан — лазейки нет. Не путать с паролями |
| `VOZVRAT_INSTRUKCIYA` | как покупателю отправить возврат — уходит в письме и на странице заказа |
| `VOZVRAT_DNEY` | сколько дней после выдачи можно оформить возврат, по умолчанию 7 |
| `EMAIL_ZAKAZY` | куда слать владельцу сводку о каждом новом заказе (`subscribers/zakaz-vladelcu.ts`). Не задан — только колокольчик в админке. Не путать с `EMAIL_TREVOGA`: там тревоги |

Шлём со служебного `zakaz@`, а отвечать просим на `info@`: живая переписка не мешается с автоматикой и не страдает от её репутации, если рассылка попадёт под подозрение почтовиков.

Письмо свёрстано таблицами, стили встроены в теги — почтовые программы вырезают внешние стили и ломают современную вёрстку. Есть текстовая версия для тех, кто читает почту без картинок.

Ошибку отправки подписчик не пробрасывает: заказ уже принят и оплачен, падать из-за недоступной почты нельзя. Неудача пишется в журнал — по нему видно, что письмо не ушло.

Перед запуском в домене нужны DKIM и DMARC (см. «Оформление сайта»), иначе письма пойдут в спам.

## Картинки и проверка сценариев

**Картинки ужимает Next** (`next.config.js`, раздел `images`): под ширину показа и в WebP. Готовые варианты лежат в `apps/storefront/.next/cache/images` и живут месяц. После `rm -rf .next/cache` при выкатке они пересчитываются при первых заходах — первые минуты страницы чуть медленнее, сервер чуть нагружен. Фотографии берутся с адреса из `NEXT_PUBLIC_MEDUSA_BACKEND_URL`, при переезде на volento.com отдельно ничего править не нужно.

**Сценарии покупателя** — `e2e/` (Playwright): навигация, корзина, оформление до оплаты, телефон, медленная сеть. Заказов и оплат не делают. Как запустить на сервере — `e2e/README.md`. Браузер стоит в `/root/pw` вместе с нужными библиотеками и шрифтами, в систему ничего не ставилось.
